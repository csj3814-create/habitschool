## 0. 실제로 잰 것

### 앱을 열 때 로그인 화면이 보이는 시간 (운영 habitschool.web.app, 로그아웃 상태로 측정)

Playwright 로 운영 페이지를 열고, 로그인 화면이 처음 그려지는 때(첫 화면)와 Firebase 가 로그인 여부를 정하는 때를 쟀다.
"휴대폰 흉내" 는 4G(지연 70ms, 9Mbps) + CPU 4배 느리게.

| 경우 | 첫 화면(=로그인 화면이 보이기 시작) | 로그인 판정 끝 | 로그인 화면이 보이는 시간 |
|---|---|---|---|
| 다시 열기, 이 PC | 0.5~0.8초 | 1.4~2.0초 | 약 0.7~1.3초 |
| **다시 열기, 휴대폰 흉내** | 1.1~1.4초 | 2.8~3.3초 | **약 1.7~2.0초** |
| 처음 열기(캐시 없음), 휴대폰 흉내 | 2.0~3.7초 | 8.4~10.3초 | 약 6~8초 |

**로그인한 회원은 여기에 왕복 두 번이 더 붙는다.** Firebase 는 저장된 로그인을 꺼낸 뒤
① 토큰이 1시간 넘었으면 새로 받고(securetoken) ② 계정이 살아 있는지 묻는다(accounts:lookup)
— 이 둘이 끝나야 "로그인됨" 을 알린다(`@firebase/auth` `initializeCurrentUser` → `reloadAndSetCurrentUserOrClear`).
이 PC 에서 잰 왕복은 각각 **0.55~0.62초**(가끔 1.5초). 아침에 처음 여는 회원은 토큰이 지나 있으니 둘 다 탄다.
→ **로그인한 회원이 휴대폰에서 다시 열 때 로그인 화면을 보는 시간 ≈ 2.5~3.5초**로 본다.

왜 이렇게 늦게 시작하나: 로그인 확인(`firebase-config.js` 의 `getAuth`)은 **앱 코드 전체(app-core.js 3만2천 줄 등)를 다
내려받은 뒤에야** 돈다(ES 모듈은 import 한 것을 전부 받은 다음 실행한다). 표의 "로그인 판정 끝" 이 늘 app-core.js
도착 직후인 이유다. 측정 브라우저 안에서만 로그인 모듈을 먼저 실행하게 끼워 넣어 봤는데 **뚜렷한 차이가 없었다**
(다시 열기 휴대폰 2.6~3.4초 vs 3.0~3.3초). 그래서 "확인을 빨리" 가 아니라 "확인하는 동안 로그인 화면을 안 보이기" 로 간다.

못 잰 것:
- 실제 갤럭시·Play 앱(TWA)에서의 시간. TWA 는 크롬을 깨우는 시간이 앞에 더 붙는다. 스테이징에 올린 뒤 대표 폰에서 확인 필요.
- 로그인한 상태의 전체 시간. 로그인은 대표 계정으로만 가능해서, 위 왕복 시간을 더해 추정했다.
- AI 분류(`classifySharedHealthImage`)에 걸리는 시간. 운영 로그 읽기 권한이 서비스 계정에 없다(`Permission denied for all log views`).
  → 구현 첫 단계에 걸린 시간을 콘솔에 남겨 스테이징에서 잰다.

측정 스크립트: 세션 scratchpad 의 `measure-auth.js` (저장소에는 넣지 않음).

## 1. 공유 → 해빛스쿨 할 때 로그인 화면

### 지금 흐름 (Play 앱 기준)

1. 갤러리에서 공유 → Play 앱(`HabitschoolLauncherActivity`)이 받는다.
2. 앱이 파일을 서버(`receiveSharedUpload`)에 올리고 무작위 id 를 받는다. 실패하면 예전 길(크롬 → 서비스 워커 `/share-target`).
3. 앱이 `/?tab=diet&focus=shared-upload&sharedUploads=<id>&shareFrom=<보낸 앱>` 으로 웹을 **새로 연다**(TWA).
4. 웹 페이지가 처음부터 다시 그려진다 → **로그인 화면(`#login-modal`, CSS 기본값 `display:flex`)이 먼저 보인다.**
5. Firebase 가 로그인을 확인하면(`onAuthStateChanged(user)`) 로그인 화면을 걷고, 120ms 뒤 `handleAppEntryDeepLink` →
   `handleSharedUploadDeepLink`.
6. 오늘 기록을 먼저 다 읽고(`loadDataForSelectedDate`) → 서버에서 파일을 받아 오고(`claimSharedUpload`, 받는 즉시 서버에서 지움)
   → 체성분 CSV/Fitdays 면 바로 체성분, 아니면 "어디에 넣을까요?" 시트 + AI 분류.

즉 **로그인 화면은 보안 때문에 일부러 띄우는 게 아니다.** 앱을 열 때마다 생기는 것과 똑같은 깜빡임이고,
공유는 매번 페이지를 새로 열기 때문에 매번 보인다.

### 지금 이렇게 되어 있는 이유 (깨면 안 되는 것)

- **파일은 로그인한 회원만 받아 간다** (`claimSharedUpload` 가 `request.auth.uid` 를 요구). 올리는 쪽(Play 앱)은 Firebase
  로그인을 모르기 때문에, 받는 쪽에서 로그인을 확인해야 회원 건강 사진이 아무에게나 넘어가지 않는다. id 는 추측할 수 없는
  128비트, 한 번 받으면 바로 지우고, 안 받아 가도 1시간 뒤 지운다. → **그대로 둔다.**
- **로그인이 확인되기 전에는 아무것도 받지도 넣지도 않는다.** 받아 간 사진은 그때 로그인된 계정의 오늘 기록에 들어간다.
  확인 전에 넣으면 "어느 계정에 넣는지" 가 불분명해진다(데이터 섞임). → **그대로 둔다.**
- **오늘 기록을 먼저 읽고 넣는다.** 어느 식단 칸이 비었는지 알아야 하고, 날짜를 오늘로 맞춰야 한다.
  → 넣는 순서는 그대로. 다만 받기·분류는 기록 읽기와 **동시에** 시작해도 된다(받기는 칸과 무관).
- 로그아웃 상태로 공유하면: 로그인 화면이 뜨고, 로그인하면 주소에 남은 id 로 이어서 받는다(1시간 안). → 그대로.

### 바꿀 것

1. **"이 기기에서 로그인했었다" 표시**: 로그인이 확인될 때마다 `localStorage` 에 `{ uid, at }` 를 적고, 로그아웃되면 지운다.
   이 표시는 화면을 어떻게 보일지만 정한다. 권한은 하나도 주지 않는다(데이터 읽기·쓰기는 여전히 Firebase 로그인과 서버 규칙이 막는다).
2. **head 의 인라인 스크립트**가 첫 화면 전에 이 표시를 보고 `<html>` 에 `auth-restoring` 을 붙인다.
   CSS: `html.auth-restoring #login-modal { display:none !important }`.
   이미 쓰고 있는 방식이다 — 카메라에서 돌아올 때 로그인 화면을 숨기는 `media-picker-auth-recovery`(index.html 755줄)와 같은 모양.
3. 공유로 들어온 경우(`focus=shared-upload`)에는 그 자리에 **"공유한 사진을 가져오는 중…"** 작은 안내를 보인다.
4. 로그인 확인이 끝나면:
   - 로그인됨 → `auth-restoring` 을 떼고 지금과 똑같이 진행.
   - 로그아웃(토큰 취소·계정 삭제 등) → 떼고 **지금처럼 로그인 화면**. 표시도 지운다.
   - 12초가 지나도 답이 없으면(모듈을 못 받는 등) → 떼고 지금처럼 로그인 화면 + 콘솔 경고. 즉 최악이 지금과 같다.
5. 공유 처리에서 `claimSharedUpload`(+AI 분류)를 오늘 기록 읽기와 동시에 시작한다. 칸에 넣는 것은 지금처럼 기록을 다 읽은 뒤.

## 2. 평소 앱을 열 때

원인은 1과 같다. 바꿀 것도 1의 1·2·4번을 앱 시작 전체에 쓰는 것이다.
로그인했던 회원은 로그인 화면 대신 앱 머리(이름·날짜 칸)와 평소 열리는 탭이 바로 보이고, 1~3초 뒤 내용이 채워진다.

### 지금 이렇게 되어 있는 이유와 지킬 것

- 로그인 화면이 기본으로 보이는 건 "모르면 로그인 화면" 이 가장 안전한 기본값이어서다. 표시가 없으면(처음 온 사람,
  로그아웃한 사람, 다른 브라우저) **지금과 똑같다.** 체험 화면(guest demo) 복원도 표시가 없는 사람에게만 그대로.
- 구글 리디렉트 로그인 복원(lessons 187·189·193·199), 카메라 복귀 복원(208·212·213)은 이미 각자 로그인 화면을 숨긴다.
  새 표시는 이 둘을 대신하지 않고 겹쳐서 같이 산다(셋 중 하나라도 켜져 있으면 숨김, 로그아웃 판정 때 각자 정리).
- 영어 앱(/en)은 이미 판정 전에 화면 전체를 숨긴다(`auth-pending`). **이번에는 손대지 않는다.**
- 공용 기기: 로그아웃하면 표시가 지워지므로 다음 사람에게는 로그인 화면이 바로 보인다.
- 판정 전에 회원 정보를 새로 그리지 않는다. 지금도 판정 뒤에 그리는 것(이름·포인트·기록)은 그대로 판정 뒤에 그린다.

## 3. 공유 사진을 AI 로 알아서 넣기

### 지금 흐름

1. 체성분 CSV → 바로 체성분. Fitdays 에서 온 사진 → 바로 체성분(동의 확인 후).
2. 그 밖 → 시트("식단 / 운동 / 수면 / 체성분") + 첫 사진 1장만 AI 분류(`classifySharedHealthImage`, gemini-2.5-flash, 생각 끔).
3. 자동으로 넣는 조건(`app-core.js` 540줄):
   - 확신 ≥ 0.85 **그리고 시트를 연 뒤 1.8초 안에** 답이 왔을 때.
   - 체성분은 확신 ≥ 0.5 이면 시간과 상관없이.
   - 회원이 먼저 누르면 자동 안 함.
4. 넣으면: 식단 = 빈 칸에 **아침→점심→저녁→간식 순서로** 촬영 시간순으로 채움 / 운동 = 걸음 캡처면 걸음 판독(못 읽으면 운동 사진),
   아니면 유산소 칸 / 수면 = 수면 사진 칸(첫 장만, **있던 사진을 바꿔 끼움**).
5. 어느 경우든 **칸을 채울 뿐 저장은 회원이 누른다**(사진은 미리 저장소에 올라가지만 기록 문서는 저장 버튼 때 쓰인다).

### 찾은 문제

- **자동이 거의 안 걸린다(추정).** 1.8초 안에 사진 줄이기(1280px) + 올리기 + 서울 함수 + 모델 응답이 다 끝나야 한다.
  이 분류 함수 자체가 20초 제한·14초 마감선으로 잡혀 있다. 1.8초 안에 오는 일은 드물 것으로 본다 — 로그 권한이 없어
  수치는 못 봤다. 구현 4단계에서 걸린 시간을 콘솔에 남겨 스테이징에서 확인한다.
- **체성분 자동은 한 번도 안 걸린다(버그).** 서버는 `body` 를 돌려주는데 화면 쪽 `normalizeSharedImportClassification` 이
  `['diet','exercise','sleep']` 만 받아서 `body` 를 `unknown` 으로 바꾼다. 9/23 에 넣은 "체성분은 기준을 낮춰 바로" 가
  죽어 있다. (Fitdays 에서 온 것은 보낸 앱 이름으로 따로 가서 영향 없음.)
- **식단 칸이 시간과 안 맞는다.** 저녁에 찍은 사진을 공유해도 아침 칸이 비어 있으면 아침 칸에 들어간다.

### 1.8초 제한이 있던 이유 (지킬 것)

2026-04-15 설계 메모: "확신이 높고 **응답이 빠를 때만** 자동". 회원이 시트를 보고 고르려는 순간 화면이 다른 탭으로
휙 바뀌면, 누르려던 손가락이 엉뚱한 곳(바뀐 탭의 버튼)을 누를 수 있다. → 시간 대신 **"회원이 시트를 만졌는가"** 로 지킨다.

### 제안하는 기준

자동으로 넣는 것은 아래가 **모두** 맞을 때만. 하나라도 아니면 지금처럼 시트에서 고른다(AI 추천은 표시).

| 조건 | 기준 | 이유 |
|---|---|---|
| 확신 | 식단·운동 ≥ 0.85, 수면 ≥ 0.90, 체성분 ≥ 0.5(지금 값 유지) | 수면·걸음 캡처는 둘 다 건강앱 화면이라 헷갈리기 쉽다. 체성분은 칸만 채우고 동의·저장을 회원이 한다. |
| 회원이 시트를 안 만짐 | 시트에 손가락이 닿은 적 없음(누르기·스크롤 포함) | 1.8초 제한이 막던 "누르려는데 화면이 바뀜" 을 직접 막는다. 시간 제한은 없앤다. |
| 넣을 자리가 비어 있음 | 식단: 고른 칸이 비어 있음 / 수면: 오늘 수면 사진이 없음 / 운동: 항상 새 칸 | 있던 기록을 자동으로 바꿔 끼우지 않는다. |
| 사진 수 | 1장 (여러 장은 아래 선택지) | 지금 분류는 첫 장만 본다. 나머지가 다른 종류일 수 있다. |
| 마감 | 분류가 15초 안에 옴 | 그보다 늦으면 시트에서 고르게 둔다(무한정 기다리지 않음). |

자동으로 넣은 뒤에는 토스트로 **어디에 넣었는지와 빼는 법**을 말한다("AI가 점심 칸에 넣었어요. 아니면 사진의 ✕ 로 빼 주세요").
저장은 여전히 회원이 누른다.

### 식단 "어느 칸" — 철회 (구현하지 않음)

> 구현 중 확인: 식단 칸의 이름은 `① 첫 번째 식사 ~ ④ 네 번째 식사` 다(index.html, 2026-03-12 부터). 코드 안 이름만
> breakfast·lunch 일 뿐 화면은 끼니 순서다. 낮 12시에 첫 끼를 먹은 회원의 사진이 ② 칸에 들어가면 오히려 틀린다.
> 그래서 공유든 사진 고르기든 지금처럼 **찍은 시간순으로 다음 빈 칸**에 넣는다. 아래는 처음 적었던 안이다.

(처음 안) 공유로 들어온 식단 사진만 **찍은 시간으로 칸을 고른다**. (사진 고르기 버튼으로 여러 장 고를 때는 지금처럼 앞 칸부터 — 바꾸지 않음.)

- 찍은 시간: EXIF 촬영 시각(회원 시간대로 환산). EXIF 가 없으면(캡처 등) 칸을 시간으로 고르지 않고 지금처럼 앞 칸부터.
- 시간대(회원 시간대 기준): 04:00~10:59 아침 · 11:00~14:59 점심 · 15:00~16:59 간식 · 17:00~21:59 저녁 · 그 밖 간식.
- 그 칸이 이미 차 있으면 → 남은 빈 칸 중 앞 칸에 넣고 토스트에 그렇게 말한다(자동이 아니라 시트에서 고른 경우도 같다).
- AI 에게 간식 여부(커피·디저트·과일)를 같이 묻는 것은 **이번에는 안 한다** — 시간으로 먼저 해 보고 부족하면 다음에.

바뀐 것
- `index.html` head: 로그인했던 표시(`habitschool-signed-in-hint-v1`, 60일)가 있으면 `html.auth-restoring` → 로그인 화면 숨김.

- `js/app-core.js` 공유 처리: 사진 받기(`claimSharedUpload`)를 오늘 기록 읽기와 동시에 시작. 칸에 넣는 것은 여전히 기록을 다 읽은 뒤.
- `js/shared-import-routing.js`(새 파일): 분류 결과 받기(체성분 `body` 버그 수정)와 자동 넣기 판단.
  자동 = 확신(식단·운동 0.85 / 수면 0.9 / 체성분 0.5) + 시트를 안 만짐 + 1장 + 15초 안 + 넣을 자리 비어 있음.
  자동으로 넣으면 "AI가 ○○ 칸에 넣었어요. 아니면 ✕ 로 빼 주세요." 분류마다 걸린 시간·판단을 `console.info('[shared-import] 분류', …)` 로 남긴다.
- 지금과 달라지는 점 하나: 체성분도 이제 "시트를 만졌거나 여러 장이면" 자동으로 넣지 않는다(예전 코드는 시간과 상관없이 넣으려 했지만 버그로 실제로는 한 번도 안 넣었다).
