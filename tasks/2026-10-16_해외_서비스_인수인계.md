## 1단계(시간대)에서 꼭 지킬 것

- **기존 회원 무변화.** 시간대 값이 없으면 `Asia/Seoul`. 한국 회원의 날짜·점수·연속 기록이 하나라도 달라지면 안 된다.
- **이미 저장된 기록은 건드리지 않는다.** `daily_logs` 문서 ID 는 `${uid}_${YYYY-MM-DD}`(KST 날짜)다. 옛 기록을 다시 계산하거나 옮기지 않는다.
- **포인트 악용 막기.** 시간대를 바꿔 하루를 두 번 받는 일이 없어야 한다. 서버가 회원 시간대 기준으로 날짜를 검증하고, 시간대 변경은 횟수·주기를 제한한다(예: 30일에 한 번). 바꾸는 날의 처리 방식도 설계에 적는다.
- **서버 정산이 기준.** 화면 계산과 서버 계산(functions/points-utils.js, functions/runtime.js 등)이 같은 함수를 쓰게 한다. 예약 함수(schedule, timeZone 'Asia/Seoul')는 "모든 회원 동시 실행"인지 "회원별 자정"인지 따로 정한다.
- **알림 시각**(정해진 시각에 보내는 알림이 있다면)도 회원 시간대로 보내야 하는지 조사 목록에 넣는다.
- 새 Firestore 필드(예: `users/{uid}.timeZone`)는 `firestore.rules` 화이트리스트에 넣고 **규칙 배포는 따로 승인**받는다. 규칙 없이 코드만 올리면 저장이 조용히 거부된다(CLAUDE.md 2026-08-15 사례).

## 이 프로젝트의 작업 규칙 (요약 — 원문은 CLAUDE.md)

- 배포는 스테이징 먼저. 운영은 대표가 스테이징을 보고 "운영" 이라고 할 때만.
- Functions 배포는 exit 0 이어도 일부 함수가 빠질 수 있다. hosting 과 functions 를 따로 올리고, 로그에서 함수마다 성공 줄을 확인하고, 빠진 것은 `--only functions:A,functions:B` 로 다시 올린다. 올린 뒤 `sw.js` 의 CACHE_NAME 을 확인한다.
- 화면 파일을 바꾸면 에셋 버전을 올린다(`?v=NNN` 전부 + `sw.js` CACHE_NAME). 지금 v515. main 에 다른 작업이 먼저 들어가 있으면 그 번호보다 크게.
- `index.html` 을 바꾸면 `npm run build:en` 후 `npm run check:en`.
- 테스트: `npx vitest run` 전부 통과(현재 2,762개). 워크트리에서는 `node_modules`, `functions/node_modules` 를 메인 폴더 것으로 junction 연결해서 돌리고, 끝나면 연결을 지운다.
- Gemini 는 `gemini-2.5-flash` 만. Firebase SDK 는 12.19.0 만.
- 오류를 삼키는 `catch(() => {})` 를 새로 만들지 않는다.
- 메인 작업 폴더(`C:/SJ/antigravity/habitschool`)에서 stash·reset·checkout 하지 않는다. 다른 세션이 쓰고 있을 수 있다.
- main 은 다른 세션이 계속 올린다. 브랜치를 오래 두면 충돌이 커지니 자주 `origin/main` 을 합친다.
