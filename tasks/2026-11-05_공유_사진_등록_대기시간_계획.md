# 공유한 사진 등록할 때 기다리는 시간 줄이기 — 계획

- 작성: 2026-11-05 · 기준 코드: `origin/main` `a7f9aa52`(자산 v578). 공유 경로 코드는 v577·v578 사이에 바뀌지 않았다.
- **상태: 1차 구현함(자산 v579, 대표 11/06 「1차 시작」). 배포 전.** 2차(AAB)는 시작 안 함.
- 대표 요청: 식단·운동·수면 사진을 앱으로 공유해 등록할 때 단계마다 오래 걸린다.

## 결론

**갤러리에서 공유한 뒤 AI 분류가 끝나기까지 지금 16초(중앙값)다. 앱 업데이트 없이 약 10초, 앱 업데이트까지 하면 약 8초로 줄일 수 있다(추정).**

시간을 가장 많이 쓰는 세 곳:

1. **앱 열기~웹 준비 6.8초** — 앱을 열 때마다 앱 코드를 전부 다시 받는다.
2. **사진 한 장이 폰과 서버를 여러 번 오간다** — 폰 → 서버 → 폰 → 분류 서버, 그리고 폰 → 저장소.
3. **기록을 두 번 읽는다** — 시트와 분류가 그만큼 늦어진다.

## 1. 단계별 시간

**실측**은 운영 Cloud Run 요청 로그 30일치(10/07~11/05, 공유 71건, 소수 회원의 기록일 수 있음)의 중앙값이다. 괄호는 90%값이다.
로그는 서버에서 본 시간이라, 폰에서 느끼는 시간은 조금 더 길다.

## 3. 아직 숫자가 없는 단계를 재는 법

**1차 배포에 함께 넣었다.** "지금" 값은 위 서버 로그(30일치)를 쓴다.

**① 단계 기록 `reportSharedImportTiming`** (처음 계획의 GA 이벤트 `shared_import_step` 을 바꿨다)

- 바꾼 이유: 등록하지 않은 GA 매개변수는 나눠 볼 수 없고(`js/product-events.js` 의 첫 기록 설명), 공유가 한 달 수십 건뿐이라 동의한 회원만 세면 표본이 너무 적다. 서버 로그에 한 건당 한 줄을 남겨 한 건도 놓치지 않고 정확한 값을 본다.
- 찾는 법: Cloud Logging 에서 `resource.labels.service_name="reportsharedimporttiming"` · `[shared-import-timing]`.
- `steps`: `app_code_ready` · `auth_ready` · `claim_done` · `daily_log_ready` · `sheet_open` · `classify_done` · `target_set` · `upload_done` · `analysis_done` · `save_click` · `save_ready` · `save_done`. 값은 페이지가 열린 때부터의 밀리초다.
- 함께 남기는 것: `trace`(이 공유 한 건의 무작위 값) · `outcome` · `classify`(server·client) · `target` · `method`(auto·tap) · `network` · `worker` · `files` · `kb` · `version`.
- uid·이름·사진·건강 수치는 받지도 남기지도 않는다. 서버가 목록에 없는 값을 버린다. 같은 값이 `console.info('[shared-import] 단계', …)` 로도 남아 오류 제보에 실린다.
- 시작점은 웹 첫 시각(`performance.timeOrigin`). 2차 AAB 에서 앱이 주소에 공유 받은 시각을 실으면 0단계까지 이어진다.

**② 대표 폰 한 번 재기** (AAB 불필요, 위 ①로 못 보는 0단계용)

```bash
adb logcat -v time -s HabitschoolLauncher SharedUploadClient ActivityTaskManager
```

앱 시작·`Share delivered by upload`·`Launching TWA` 시각을 본다. 웹 쪽은 `chrome://inspect` 로 연결해 함께 본다. 와이파이·LTE 를 나눠 식단 사진 큰 것과 캡처를 각 3회.

**③ 서버 쪽 다시 집계** (읽기 전용, 코드 변경 없음)

Cloud Logging `run.googleapis.com/requests` 를 `service_name` 별로 읽어 `httpRequest.latency` 를 본다. 대상은 `receivesharedupload` · `claimsharedupload` · `classifysharedhealthimage` · `analyzediet` · `analyzeexercise` · `analyzesleepmind`.
콜드 스타트는 `run.googleapis.com/varlog/system` 의 `Starting new instance` 로 가른다. 1분당 읽기 한도가 낮아 천천히 읽어야 한다. 사용자 정보를 출력하지 않는다.

**확인할 것 하나:** 크롬이 공유 파일 버리는 문제(crbug 548571656)가 고쳐졌는지 대표 폰에서 본다. 고쳐졌으면 서버를 거치지 않는 옛 길(서비스 워커)을 다시 쓸 수 있어 1·3단계와 파일 왕복이 통째로 사라진다. 그때는 3번 대신 이 길을 고른다.

## 못 잰 것

- 실제 폰에서 느끼는 시간. 위 숫자는 서버 로그와 PC 흉내 측정이다.
- 0단계, 8단계, 자동 넣기 비율(제보 콘솔 1건뿐).
- 2단계를 나눈 시간(크롬 깨우기·로그인 복원). 예전 측정(10/20)의 로그인 복원 왕복은 각 0.6초 안팎이다.
- 단계 간격은 사람을 구분하지 않고 가까운 시각끼리 짝지었다. 공유가 드물어 크게 틀리지 않지만, 동시에 다른 사람이 쓰면 섞인다.
