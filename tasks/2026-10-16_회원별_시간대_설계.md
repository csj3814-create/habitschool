## 0. 한 줄 요약

지금 앱은 "오늘이 며칠인가"를 모두 한국 시간으로 정한다. 이걸 **회원마다 저장된 시간대로**
정하게 바꾼다. 시간대가 저장되지 않은 회원(= 지금 한국 회원 전원)은 `Asia/Seoul` 로 계산하므로
아무것도 달라지지 않는다.

## 1. 조사에서 알게 된 것

### 1-1. 바꿀 곳은 "지금이 며칠·몇 시인가"를 정하는 자리뿐이다

KST 를 쓰는 자리는 약 400곳(화면 약 25개 파일, 서버 약 12개 파일, 일회용 scripts 약 20개)이지만
종류는 셋뿐이다.

| 종류 | 예 | 시간대 영향 |
|---|---|---|
| ① 날짜 글자에 하루 더하기·빼기 | `addDaysToKstDateString('2026-10-16', -1)` | **없음.** 달력 계산이라 어느 나라든 같다. 이름에 KST 가 붙어 있을 뿐이다 |
| ② 지금 → 오늘 날짜 / 지금 몇 시 | `getKstDateString()`, `getCurrentKstDateString()`, `getKstHour()` | **있음.** 바꿔야 할 핵심 |
| ③ 어떤 시각 → 그 시각의 날짜 | 사진 업로드 시각, 헬스커넥트 수면이 끝난 시각 → 날짜 | **있음.** ②와 같이 바꾼다 |

그래서 실제로 손댈 곳은 ②·③ 이고, 이것들을 **하나의 함수 묶음**(`member-time`)으로 모으면 된다.

### 1-2. 기록 문서의 날짜는 "회원이 고른 날짜 글자"다

`daily_logs/{uid}_{YYYY-MM-DD}` 의 날짜는 화면에서 고른 날짜 글자 그대로다. 서버는 이 글자를
다시 계산하지 않는다. 해외 회원의 새 기록은 그 회원의 현지 날짜 글자로 저장되면 되고,
**옛 기록은 건드릴 이유가 없다.**

보안 규칙(`firestore.rules:156-171`)은 날짜 형식과 2024~2030 범위만 본다. "오늘인가"는 서버
`awardPoints` 가 포인트를 줄 때 판단한다 — 이 판단만 회원 시간대로 바꾸면 된다.

### 1-3. 이미 해외 사용자를 위한 장치가 일부 있다

- `js/app-core.js:10077` `isDeviceOutsideKoreaTime()` — 기기 시간대가 한국이 아니면 날짜 옆에 `KST`
  배지를 띄우고, 누르면 "기록 날짜는 한국 시간 기준" 이라고 알려 준다(`updateKstBasisBadge`).
- `js/app-core.js:10183` `convertLocalCaptureToKstParts()` — 사진 촬영 시각(EXIF, 현지 시각)을
  KST 로 바꿔 날짜를 비교한다. 캐나다 회원 사진이 막히던 문제를 고친 것.

이번 작업은 이 장치들을 "KST 로 환산" 에서 "**회원 시간대로** 환산" 으로 바꾸는 것이다.

### 1-4. 해외에서 지금 실제로 생기는 문제 (예: 미국 서부 회원, 한국보다 16시간 늦음)

- 현지 오전 8시 = 한국 자정. 이때부터 앱의 "오늘"이 하루 넘어가 **현지 아침에 날짜가 바뀐다.**
- 서버는 "한국 기준 어제~오늘" 날짜의 기록에만 포인트를 준다. 서쪽 회원은 대체로 들어오지만,
  **동쪽 회원(뉴질랜드 등)은 현지 오늘 기록이 "한국 기준 내일"이라 포인트가 거부된다.**
- 알림이 한국 시각 기준이다. 연속 기록 알림 "오늘 밤에 끊겨요"(한국 밤 10시)가 미국 서부에는
  **아침 6시**에 간다.

## 3. 설계

### 3-1. 저장하는 값

`users/{uid}` 에 서버만 쓰는 필드를 더한다.

| 필드 | 뜻 |
|---|---|
| `timeZone` | IANA 이름(예: `America/Los_Angeles`). **없으면 `Asia/Seoul`** |
| `timeZoneChangedAt` | 마지막으로 바꾼 시각 (서버 시각) |
| `timeZonePrevious` | 바꾸기 전 값 (문의 대응용) |

- **회원이 직접 쓰지 못한다.** 새 함수 `setMemberTimeZone`(callable)만 쓴다. 서버가 이름이 맞는지,
  30일이 지났는지 검사한다.
- 그래서 `firestore.rules` 화이트리스트에 **넣지 않는다.** 넣지 않은 필드는 회원이 쓰려 하면 거부되는데,
  그게 바로 원하는 동작이다. → **이번 단계는 규칙 배포가 필요 없다.** (2026-08-15 사례 같은 조용한 거부가
  생길 자리가 없다. 서버 함수는 관리자 권한이라 규칙을 거치지 않는다.)
- 이미 저장된 기록·필드는 하나도 옮기거나 다시 계산하지 않는다.

### 3-2. 하나의 함수 묶음 `member-time`

화면 `js/member-time.js`(ESM) 와 서버 `functions/member-time.js`(CommonJS) 에 **같은 코드**를 둔다.
(서버 배포에는 `functions/` 만 올라가므로 한 파일을 같이 쓸 수 없다 — `streak-freshness.js` ↔
`activity-days.js` 와 같은 방식.) 테스트가 두 파일을 같은 입력 수천 개로 돌려 **답이 같은지** 확인한다.

```
DEFAULT_TIME_ZONE = 'Asia/Seoul'
normalizeTimeZone(value)            → 올바른 IANA 이름이면 그 이름, 아니면 'Asia/Seoul'
getMemberTimeZone(userData)         → normalizeTimeZone(userData?.timeZone)
getDateStringInZone(instant, tz)    → 'YYYY-MM-DD'
getHourInZone(instant, tz)          → 0~23
getMinutesOfDayInZone(instant, tz)  → 0~1439
getMemberToday(userData, now)       → 회원의 오늘
getMemberYesterday(userData, now)   → 회원의 어제
canChangeTimeZone(userData, now)    → { allowed, nextAllowedAt }
```

- 계산은 `Intl.DateTimeFormat` 으로 한다(서머타임 자동 처리). 시간대마다 포매터를 한 번만 만들어 둔다.
- `Asia/Seoul` 일 때 결과가 지금 함수들(`+9시간` 방식)과 **완전히 같다**는 것을 테스트로 고정한다.
  한국은 1988년 이후 서머타임이 없어 두 방식이 같은 답을 낸다.

### 3-3. 화면

1. 로그인 후 회원 문서를 읽으면 `setActiveMemberTimeZone(tz)` 로 앱 전체의 "오늘" 기준을 정한다.
   다음 실행 때 깜빡임이 없도록 회원별로 `localStorage` 에도 둔다(없거나 읽기 실패하면 `Asia/Seoul`).
2. `getKstDateString` 등 2-B 의 함수들은 이 기준을 쓴다. 이름은 `getTodayString` 처럼 뜻에 맞게 바꾸고,
   호출부는 기계적으로 바꾼다(동작이 같다는 것은 테스트가 증명).
3. 시간대 바꾸기 화면 — 최소한으로:
   - 날짜 옆 배지: 기기 시간대 ≠ 회원 시간대일 때만 보인다(한국 회원이 한국에 있으면 지금처럼 안 보임).
     누르면 "지금 기록 날짜 기준: 한국 시간. 기기 시간(미국 태평양)으로 바꿀까요? 바꾸면 30일 동안
     다시 바꿀 수 없어요" → 확인하면 `setMemberTimeZone`.
   - 프로필 설정에 "기록 시간대" 한 줄(현재 값 + 바꾸기).
4. 영어 화면(`/en`)도 같은 문구를 `i18n` 에 넣는다. `index.html` 을 바꾸므로 `build:en`·`check:en`.
5. 플레이 앱 HBT 잠금과는 관계없다(새 화면에 HBT 가 들어가지 않는다).

### 3-4. 서버

1. `awardPoints` 는 지금 회원 문서를 쓰기만 하고 읽지는 않는다(포인트 `increment`). 시간대를 알려면
   기록 저장마다 회원 문서 읽기가 1번 는다. 이 값으로 지급 기간·증거 검사를 한다.
2. 예약 알림 3종은 회원 목록을 읽을 때 시간대도 같이 읽어 회원 시각으로 고른다.
   "오늘 기록했나"는 한국 기준 어제·오늘·내일 세 날짜를 한 번에 읽어 회원별 오늘과 맞춘다
   (지구의 모든 시간대는 한국 날짜 ±1일 안에 있다).
3. `sendStreakAlert` 는 하루 한 번 → 매시간으로 바꾸고, "회원 시각이 22시인 사람"만 고른다.
4. 친구 챌린지·소모임 정산은 "종료일이 참가자 모두에게 지났는가"로 판정한다.

### 3-5. 악용 막기와 "바꾸는 날"

- **같은 날짜로 두 번 받을 수 없다.** 기록 문서 ID 가 `{uid}_{날짜}` 하나뿐이고, 포인트 장부도
  `point_ledger/{uid}_{날짜}` 다. 시간대를 바꿔도 같은 날짜 문서는 하나다. (지금도 그대로인 안전장치)
- **바꿀 수 있는 것은 30일에 한 번.** 서버가 `timeZoneChangedAt` 으로 막는다. 관리자는 풀 수 있다.
- 시간대를 크게 동쪽으로 옮기면 "내일 날짜"를 하루 일찍 열 수 있다(최대 1일). 그 날짜는 한 번 쓰면
  끝이라 이득은 30일에 하루치 이하다. 막으려면 복잡해지므로 **기록·관찰만** 한다
  (바꾼 회원 수와 바꾼 날 지급을 관리자 로그에 남긴다).
- **바꾸는 날의 처리:** 바꾼 순간부터 새 시간대로 계산한다. 지급 기간도 새 시간대의 어제~오늘.
  이미 받은 날짜는 그대로 남는다. 같은 날 알림이 두 번 갈 수 있는 경우(장부 날짜가 바뀌어서)는
  "바꾼 뒤 24시간 동안은 같은 종류 알림을 다시 보내지 않는다"로 막는다.
- 연속 기록: 서쪽으로 옮기면 같은 날짜가 길어지고, 동쪽으로 옮기면 하루가 짧아질 뿐 날짜를 건너뛰지는
  않는다(최대 26시간 차라 하루를 통째로 건너뛰는 일은 없다). 연속은 "어제 또는 오늘"을 보므로 끊기지 않는다.

### 3-6. 기존 한국 회원 무변화를 증명하는 테스트 (구현보다 먼저 쓴다)

1. **같은 답 테스트:** 2024~2030 사이 수천 개의 시각(한국 자정 앞뒤 1초, 매시 정각, 연말, 윤년 2/29 포함)에서
   `getDateStringInZone(t, 'Asia/Seoul')` · `getHourInZone` · `getMinutesOfDayInZone` 이 지금 함수들
   (`getCurrentKstDateString`, `getKstHour`, `+9h toISOString`)과 하나도 다르지 않다.
2. **시간대 없음 = 한국:** `timeZone` 이 없거나, 빈 값이거나, 이상한 값인 회원 문서는 모두 `Asia/Seoul` 로 계산된다.
3. **입구 테스트(시간대 없는 회원):** 같은 회원·같은 시각으로
   - 포인트 지급 기간(어제·오늘·그제·내일 날짜), 사진 업로드 시각 검사, 헬스커넥트 수면 인정
   - 연속 기록, 챌린지 시작일·같은 날 재시작·종료 판정
   - 습관 알림 대상(시각 0~23 전부), 연속 알림 대상(13:00 UTC 에만 지금과 같은 사람, 다른 시각엔 0명),
     식단 창 알림 대상
   이 바꾸기 전과 같다. 바꾸기 전 동작은 지금 코드를 그대로 불러 기준값으로 쓴다.
4. **화면·서버 같은 답:** `js/member-time.js` 와 `functions/member-time.js` 가 같은 입력에 같은 답.
5. **해외 동작:** 미국 서부·뉴질랜드·인도(30분)·서머타임 바뀌는 날에서 오늘·시각이 맞는다.
6. **악용:** 30일 안에 두 번 바꾸기 거부, 이상한 시간대 이름 거부, 회원이 `timeZone` 을 직접 쓰면
   규칙이 거부(규칙 테스트).

전체 `npx vitest run` 통과(지금 약 2,762개).

## 4. 대표 결정이 필요한 것

1. **시간대를 어떻게 정할까**
   - (추천) **회원이 고른다.** 기기 시간대가 다르면 배지에서 한 번 제안한다.
     한국 회원이 해외여행을 가도 저절로 바뀌지 않는다 → "기존 회원 무변화"가 지켜진다.
   - 자동: 기기 시간대를 그대로 저장. 편하지만 한국 회원이 여행 가면 날짜 기준이 바뀐다.
   - 절충: 새로 가입하는 회원만 기기 시간대로 시작, 기존 회원은 직접.
2. **변경 제한** — 30일에 한 번 (관리자 해제 가능). 더 짧게/길게?
3. **연속 알림을 매시간 도는 방식으로 바꿔도 될까** — 한국 회원은 같은 시각에 받는다. 함수 실행 횟수만
   하루 1번 → 24번으로 는다(비용은 거의 없음).
4. **친구 챌린지·소모임 정산** — "참가자 모두의 하루가 끝난 뒤" 원칙. 해외 참가자가 있으면 정산이
   최대 하루 늦어진다. 괜찮을까? (대안: 1단계에서는 지금처럼 한국 날짜로 정산하고, 해외 회원에게
   "친구 챌린지는 한국 날짜 기준" 이라고 안내)

## 6. 구현 기록 (2026-10-16)

대표 결정: 회원이 직접 고름 + 배지에서 제안 / 30일에 한 번 / 연속 알림 매시간 / 참가자 모두의 하루가 끝난 뒤 정산.

### 설계와 달라진 점

| 설계 | 실제 | 이유 |
|---|---|---|
| `getKstDateString` 등 이름을 뜻에 맞게 바꾼다 | **이름은 그대로**, 속만 회원 시간대로. 정의마다 "이름은 한국 시간만 쓰던 때의 것" 주석 | 기존 테스트 수십 개가 이 이름을 그대로 검사한다. 이름을 바꾸면 기존 테스트를 고쳐야 하고, 그만큼 "아무것도 안 바뀌었다" 는 증거가 약해진다 |
| 프로필에 "기록 시간대" 한 줄 | **만들지 않음.** 날짜 옆 배지 하나로 보고·바꾼다 | 배지는 기기 시계 ≠ 기록 기준 시계일 때만 뜬다 — 해외에 사는 회원, 해외에서 돌아온 회원 모두 거기서 바꿀 수 있다. 한국 회원이 보는 화면은 한 픽셀도 바뀌지 않는다 |
| 배지: 기기 시간대 이름 ≠ 회원 시간대 이름 | 이름이 아니라 **지금 시계**를 비교 | 바꾸기 전 `isDeviceOutsideKoreaTime` 도 시계로 비교했다. 이름으로 비교하면 일본에 있는 한국 회원에게 배지가 새로 뜬다 |
| 소모임은 친구 챌린지와 같은 "참가자 모두" 원칙 | 소모임 진행은 **회원별 문서**(시작일·종료일이 회원마다)라 회원 본인의 오늘로 판단 | 코드를 보니 공동 정산이 아니었다 |
| 커뮤니티 통계의 연속 계산(`collectCurrentStreaks`)을 회원 날짜로 | **그대로(한국 날짜)** | 전체 통계다(A 묶음). 해외 회원의 연속이 통계에서 최대 하루 어긋나는 정도 |
| 관리자 해제 기능 | 화면은 만들지 않음. Firestore 에서 `users/{uid}.timeZoneChangedAt` 을 지우면 풀린다 | 해외 회원 수가 아직 적다 |

그대로 둔 것(설계 A 묶음 그대로): HBT 거래 기록의 `date` 글자(전환 한도는 계약의 UTC 하루), 반응 포인트 장부 날짜,
관리자 화면, 재방문 메일, 분석 기록(`recordWebPlatform` 등), 주간 베스트 갤러리, 커뮤니티 통계.

### 만든 것

- `functions/member-time.js` · `js/member-time.js` — 공통 계산(글자 하나까지 같음, 테스트가 확인). 화면 쪽은 지금 회원의
  시간대를 `globalThis` 에 둔다(`?v=` 가 다른 모듈 두 벌이 떠도 앱의 "오늘" 은 하나).
