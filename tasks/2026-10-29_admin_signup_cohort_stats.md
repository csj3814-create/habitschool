**포인트 정산 시각을 쓰지 말라는 요청이 맞는 이유:**

- 회원 현지 기준 어제·오늘 기록만 정산하고 (`points-utils.js:187`)
- 8,000보 자동 가져오기도 정산하며
- 같은 증거가 다시 와도 정산하지 않는다.

그래서 "첫 실천 저장"과 의미가 다르다. 대체값으로 쓰지 않는다.

## 2. 우선 제안 (1안) — 관리자용 기간별 가입·출처 합계

**새 계측 없이** 지금 있는 자료만으로 한다.

### 무엇을 만드나
- **서버 콜러블** `getAdminSignupCohort({ startDate, endDate })` (KST `YYYY-MM-DD`, 포함 구간)
  - `assertAdminRequest`로 막는다. 기존 관리자 콜러블과 같은 방식이다.
  - `admin.auth().listUsers()`로 Auth 계정을 모두 읽고, `creationTime`을 KST로 바꿔 기간 안의 계정을 고른다. 1,000명 단위로 페이지를 넘긴다.
  - 고른 uid의 `users` 문서에서 `createdAt`, `referredBy`, `settings.signupSource`만 `select`로 읽는다.
  - **합계만 돌려준다.** uid·이메일·이름처럼 회원별 값은 내보내지 않는다.
- **관제탑 화면** (`admin.html`): 시작일·종료일 입력, 조회 단추, 합계 표, CSV 내보내기.
  - 기존 `getAdminDashboardSnapshot`에 붙이지 않는다. 대시보드를 열 때마다 Auth 전체를 읽게 되기 때문이다.

### 결과 칸 (모두 합계)
1. **분모**
   - 기간 내 Auth 생성 계정 수
   - − 관리자(`admins`)
   - − 테스트(표식이 없으면 "제외 안 함·미확인")
   - = 집계 대상
2. **가입 시각 대조**
   - `users.createdAt`과 Auth 시각의 차이가 큰 계정 수 (기준은 결정 사항)
   - `users` 문서가 없는 Auth 계정 수 (가입을 끝내지 않음)
3. **출처 근거별 칸.** 한 사람이 여러 칸에 들어갈 수 있다. "1순위 버킷" 하나로 합치는 표는 따로 둔다.
   - 명시 태그(`src`/utm): 값별 개수
   - 앱 브라우저(`app`): 값별 개수
   - referrer 호스트: 값별 개수
   - 초대 표시(`signupSource.ref`)
4. **초대 교차표**
   - `ref`와 `referredBy` 둘 다 있음
   - `ref`만 있음
   - `referredBy`만 있음
   - 둘 다 없음
5. **결측 상태**는 "출처 미확인"과 섞지 않고 따로 센다.
   - `signupSource` 없음 — 9/27 전 가입(수집 전)
   - `signupSource` 없음 — 9/27 이후 가입(결측)
   - `late:true` (늦게 채운 값)
   - 최초 방문이 가입보다 N일 이상 앞섬 (오래된 단서). N은 결정 사항이다.
6. **메타데이터** (화면과 CSV 머리에 같이 넣는다)
   - 기간, "KST 기준", 관측 종료 시각(조회 시각)
   - "현재 남아 있는 계정만 — 탈퇴자 제외"
   - 각 칸의 정의 문장, 분모

### 함께 고칠 작은 것 (스크립트만, 선택)
`scripts/signup-sources.mjs`는 일자를 UTC로 자르고(`slice(0,10)`) `late`를 무시한다. 콜러블과 같은 분류 함수를 쓰게 하면 두 숫자가 서로 맞는다.

### 영향
- **DB:** 조회 1번에 Firestore 읽기 ≈ 기간 내 가입자 수. 쓰기 0.
- **Auth:** `listUsers` 1~2회 (652명이면 1회). 추가 비용 없음.
- **규칙:** 변경 없음. 콜러블은 Admin SDK로 읽는다.
- **배포 대상:** `functions` + `hosting`. `firestore.rules`는 그대로다.

### 기대 효과
SNS를 운영한 기간별로 "가입 계정 수 + 어디서 왔다는 단서 + 그 단서를 얼마나 믿을 수 있는지"를 관제탑에서 바로 본다. 출처 미확인과 결측이 숫자로 드러나므로, 조회수를 가입으로 착각할 여지가 줄어든다.

## 3. 후속 제안 (2안) — 앞으로의 첫 실천 저장 시각 측정

### 실천으로 인정할 것 (실제 스키마 기준 초안)

지금 제품이 "기록했다"고 인정하는 기준은 포인트 계산 함수 `calculateServerAwardedPoints` (`functions/points-utils.js:344`) 하나다. 여기서 **포인트·날짜 제한만 떼고 내용 기준**만 쓰는 것을 제안한다.

| 분류 | 인정 근거 (필드) | 결정 필요 |
|---|---|---|
| 식단 | `diet.{breakfast,lunch,dinner,snack}Url` | — |
| 운동 | `exercise.cardioList[].imageUrl` / `cardioImageUrl`, `strengthList[].videoUrl` / `strengthVideoUrl` | `steps.count ≥ 8000` 자동 가져오기 인정 여부 · `exercise.healthSessions`(포인트 미인정) 인정 여부 |
| 수면 | `sleepAndMind.sleepImageUrl` | HC `sleepSync` 자동 가져오기 인정 여부 |
| 마음 | `meditationDone === true`, `gratitude`가 비어 있지 않음 | — |

**인정하지 않는 것:**
- 로그인, 단추 클릭
- 빈 문서, 기본값
- `metrics`만 있는 문서
- 분석 결과(`dietAnalysis`·`sleepAnalysis`)만 있는 문서
- 손으로 넣은 `sleepHours`
- 포인트 지급, 축하 화면 노출

**결정이 필요한 것 (지금 정책을 임의로 바꾸지 않는다):**
- **과거 날짜 보완 저장:** 날짜 선택기는 30일 전까지 허용한다 (`app-core.js:3643`). 저장 시각은 기록하되 `backdated:true`로 표시하고, 지표에 넣을지는 대표가 정한다.
- **기존 기록 수정:** 이미 증거가 있는 문서에 증거가 **새로** 더해질 때만 실천으로 본다. 메타데이터 갱신, 분석 결과 도착, 갤러리 숨기기, 서버의 `awardedPoints` 쓰기는 이전과 이후의 증거가 같으므로 세지 않는다.

### 방식
- **새 트리거는 만들지 않는다.** `daily_logs` 쓰기마다 이미 도는 `awardPoints` (`runtime.js:4741`) 맨 앞에서 작은 함수 하나를 부른다.
  - 이 함수는 포인트 자격과 상관없이, 쓰기 **전/후** 문서에서 증거 목록을 뽑아 비교한다.
  - 실패하면 `console.error`로 남기고 포인트 정산은 계속한다. 오류를 조용히 삼키지 않는다 (CLAUDE.md 8/15 교훈).
- **시각 기준:**
  - `event.time`: 문서 쓰기가 커밋된 서버 시각. 이 값을 지표에 쓴다.
  - `recordedAt`: 처리한 시각 (`serverTimestamp`). 처리 지연을 재는 데만 쓴다.
  - 회원이 고른 활동 날짜(`date`)는 시각 대신 쓰지 않고 별도 칸에 둔다.
- **중복·재시도·역순:** 문서 id를 고정하고 트랜잭션 안에서 "없으면 만든다, 있으면 더 이른 `event.time`일 때만 바꾼다"로 처리한다. 같은 이벤트가 다시 와도, 순서가 뒤바뀌어 와도 결과가 같다. 개수는 문서 수로 세므로 부풀지 않는다.

### 새 자료 (서버만 쓰는 두 컬렉션)

| 컬렉션 | 문서 id | 필드 | 쓰는 시점 |
|---|---|---|---|
| `practice_firsts` | `{uid}` | `userId`, `firstAt`(event.time), `recordedAt`, `kinds:{diet,exercise,sleep,mind}` (참/거짓만), `logDate`, `backdated` | 처음 증거가 새로 생겼을 때 1번 (더 이른 이벤트가 오면 고침) |
| `practice_days` | `{uid}_{저장 KST 날짜}` | `userId`, `saveDateKst`, `firstAt`, `kinds`, `logDate`, `backdated` | KST 하루에 처음 새 증거가 생겼을 때 1번 |

- **복제하지 않는 것:** 사진 URL, 건강 수치, 메모·감사 내용은 넣지 않는다. 종류 표시(참/거짓)와 시각뿐이다.
- **수집 대상:** 측정 시작 이후 Auth 생성 계정만으로 제한한다. 쓰기량이 줄고, 기존 회원의 옛 문서가 건드려져 "첫 실천"이 잘못 찍히는 일이 없어진다.
- **접근 권한:**
  - `firestore.rules`에 `read: if isAdmin(); write: if false`를 넣는다 (`point_ledger` 패턴).
  - 관리자 콜러블이 Admin SDK로 읽어 합계만 낸다.
- **탈퇴 시 정리:** `functions/account-deletion.js` `OWNED_QUERIES`에 `["practice_firsts","userId"]`, `["practice_days","userId"]`를 넣는다. 정책 문서와 코드의 일치는 `tests/policy-documents-match-code.test.js`가 지킨다. 개인정보처리방침에 "서비스 이용 기록" 문구가 필요한지 같이 본다.
- **예상량:** 하루 신규 가입 수명대에서
  - 읽기: 대상 회원의 `daily_logs` 쓰기 1건당 1건
  - 쓰기: 회원·하루당 최대 1건 + 회원당 최초 1건
  - 하루 수십~백여 건이다. 함수 호출 수는 늘지 않는다(기존 트리거 안에서 돈다).

### 대표가 고를 운영 선택지
- **수집 기간**
  - (a) 정해진 SNS 캠페인 동안만
  - (b) 시작일부터 계속
  - (a)는 부담이 적고, (b)는 다음 캠페인과 비교할 수 있다.
- **보관 기간**
  - (a) `practice_days`는 가입+8일까지만 두고 예약 함수로 지움, `practice_firsts`는 탈퇴 때까지
  - (b) 둘 다 90일
  - (c) 둘 다 탈퇴 때까지
  - 짧을수록 개인정보 부담이 줄고, 나중에 D30 같은 지표를 다시 계산할 수 없다.
- **처리 지연 허용:** 지표는 `event.time`으로 계산하므로, 처리가 늦어도 경계 판정은 바뀌지 않는다. 남는 결정은 "아직 처리되지 않은 이벤트가 있을 수 있는 최근 N분은 미확정으로 둘 것인가"다. 보통 트리거 지연은 수 초다. 예를 들면 관측 종료 시각 전 10분은 미확정으로 둘 수 있다.

## 4. 같은 가입 코호트의 지표 정의

- **가입 확정 시각:** Auth `creationTime`.
- **가입일:** 가입 확정 시각의 KST 날짜.
- **측정 범위:** 2안 측정 시작 시각 ~ 관측 종료 시각.

**24시간 첫 실천**
- 분모: 코호트 중 `가입시각 ≥ 측정 시작`이고 `가입시각 + 24h ≤ 관측 종료`인 사람.
- 분자: 분모 중 `practice_firsts.firstAt ∈ [가입시각, 가입시각 + 24h)`인 사람.
- 24시간이 아직 지나지 않은 사람은 **미성숙**으로 따로 센다. 0으로 세지 않는다.
- 화면 표시: "관찰 완료 n / 코호트 N", 그리고 n = N일 때만 "확정".

**정확 D7 실천**
- D7 = 가입일(KST) + 7일, 그 하루 하나.
- 분모: 관측 종료 시각이 D7+1일 00:00 KST 이후이고, 측정 시작 시각이 D7 00:00 KST 이전인 사람. 즉 측정 범위가 그 하루를 통째로 덮어야 한다.
- 분자: 분모 중 `practice_days`에 `saveDateKst == D7` 문서가 있는 사람.
- D8 이후 저장은 세지 않는다.

**비율**
- 같은 코호트·같은 관찰 범위의 분자/분모로 계산한다.
- 분모가 0이거나 측정 범위 밖이면 "**미측정**"으로 표시한다. 0%와 구분한다.

**측정 시작 전 코호트**
- 10/18~24를 비롯한 측정 시작 전 코호트는 날짜가 지나도 계속 "미측정"이다.
- 원하면 "활동일 기준 참고값"(해당 `date` 문서에 실천 증거가 있음, 저장 시각은 모름)을 **이름을 달리해서** 따로 보여 줄 수 있다. 결정 사항이다.

## 5. 검증안 (합성 자료 우선, 회원 자료·건강 내용·인증정보는 보고서에 내보내지 않음)

**순수 함수 단위 테스트** (`tests/`, vitest)
- KST 자정 경계: 가입 15:00:00Z(= KST 00:00) 대 14:59:59Z. D7 날짜 계산.
- 24시간 경계: 정확히 +24h는 제외(반열린 구간), +23:59:59는 포함.
- 정확 D7 대 D8: D7 23:59:59 KST 저장은 포함, D8 00:00:00은 제외.
- 미성숙·미측정·실제 0: 세 상태가 다른 값으로 나오는지, 분모 0이면 비율이 "미측정"인지.
- 중복·역순: 같은 이벤트 2번, 늦은 이벤트가 먼저 도착 → 문서 1개, `firstAt`은 가장 이른 값.
- 메타데이터 갱신·분석 도착·서버 `awardedPoints` 쓰기 → 실천으로 세지 않음.
- 빈 문서·기본값·HC 자동값 → 결정한 정책대로 인정/불인정.
- 관리자 제외: `admins` uid가 분모에서 빠짐.
- 출처: `signupSource` 없음(9/27 전·후), `late:true`, 오래된 `at`, `ref`만·`referredBy`만이 각각 다른 칸에 들어감.
- 탈퇴: Auth에 없는 계정은 어디에도 나오지 않고, 화면에 "탈퇴자 제외" 문구가 있음.

**에뮬레이터** (`firebase emulators:start`)
- 관리자가 아닌 계정이 콜러블을 부르면 `permission-denied`.
- 클라이언트가 `practice_*`를 읽기·쓰기 → 거부 (규칙 테스트).
- 탈퇴 함수 실행 후 `practice_*` 문서 0건.

**운영 반영 후**
- 대표 계정으로 한 번 저장하고, `practice_*`에 문서가 실제로 생겼는지 콘솔에서 본다. 규칙이 막아도 화면은 멀쩡해 보이기 때문이다.
